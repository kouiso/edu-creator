# Pre-Mortem Analysis (プレモーテム分析) — プロジェクトの目的から逆算する思考

## 核心原則

実装・バグ修正・リファクタリング・レビューなど、複数手順を伴うタスクを引き受けた場合、コードを書き始める前にそのタスクをプロジェクトの目的と照らし合わせ、プレモーテム分析を実施すること。個々のタスクの成否は、プロジェクト全体の目標という文脈の中でしか判断できない。「動いた」だけでプロジェクトの目的から遠ざかるタスクは失敗である。楽観バイアスによって、予測可能な失敗が放置されやすい。

**確信度**: High

## プレモーテムの2つの問い

### 問い1: プロジェクトレベル（戦略）

> 「このプロジェクトは目的を達成できずに終わった。何がまずかったのか？」

プロジェクトの目的が書かれた文書（CLAUDE.mdがあればそれを優先し、無ければAGENTS.md・README.mdなど実在するもの）を読み、ミッションを把握する。そのうえで、プロジェクトの最終目標が達成されなかったとしたら最も可能性の高い原因は何かを問う。実行するすべてのタスクは、この背景に照らして評価すべきである。

例：
- corporate-site: 「コーポレートサイトのリニューアルが失敗した」 → デザインがFigmaと一致しない、文言がWordPress版とずれている、フォームが壊れている、SEO/アナリティクス未設置。
- task-app: 「教育アプリが学習者の役に立たなかった」 → カリキュラムの質が低い、UXが学習者を混乱させる、機能は作ったが学習目標を支えていない。
- horsemanager: 「馬managementシステムが使い物にならなかった」 → 中核ワークフローが壊れている、データ整合性の問題、日常利用に耐えない遅さ。

この問いはセッションごと（またはプロジェクトを切り替えるたび）に1回だけ立て、以降の全判断のフィルターとして背景に置いておく。

### 問い2: タスクレベル（戦術）

> 「このタスクは完了したが、状況を悪化させた。何が起きたのか？」

目の前の個別タスクについて、具体的な失敗モードを洗い出す。些細でないタスクに着手する前には必ず問う。

## 必須のプレモーテム手順

### Step 0: プロジェクトの目的を理解する

セッション内の最初のタスクである場合、プロジェクトの目的が書かれた文書（CLAUDE.mdがあればそれを優先し、無ければAGENTS.md・README.mdなど実在するもの）を読み、次を把握する：
1. プロジェクトの最終目標は何か
2. 既知の重要成功要因は何か
3. 過去にどのような失敗・ヒヤリハットが記録されているか

この文脈が、以降のプレモーテム分析全体の土台になる。

### Step 1: プロジェクト目的との整合性チェック

タスクに着手する前に問う：

> 「このタスクを完璧にやり遂げたら、プロジェクトは目的に近づくか？」

答えが不明確なら、着手前にユーザーへ確認する。
答えがNoなら、「このタスクはプロジェクト目標『X』とズレているように見えます。進めてよろしいですか？」と提起する。

### Step 2: 失敗モードの特定（コードを書く前に）

このタスクが失敗しうる具体的なパターンを3〜5個挙げる。以下の両方の観点を含めること：
- **タスクレベルの失敗**: この実装で具体的に何がうまくいかない可能性があるか
- **プロジェクトレベルの失敗**: たとえ「完了」しても、このタスクがプロジェクトの目的をどう損ないうるか

| 悪い例（タスクのみ） | 良い例（プロジェクトを踏まえた例） |
|----------------|---------------------|
| 「ヘッダーコンポーネントが壊れるかもしれない」 | 「ヘッダー変更でSPのスティッキースクロールが壊れ、Figma差分が5%を超える。プロジェクトの成功基準No.1はFigmaとのピクセル単位の一致」 |
| 「テストが落ちるかもしれない」 | 「E2Eテストは通るが、問い合わせフォームのUXがWordPress仕様からズレる。既存サイトと違う体験になり、シームレスな移行という目標を損なう」 |
| 「リファクタリングでバグが混入するかもしれない」 | 「このリファクタリングはコード品質を上げるがリリース日を遅らせる。プロジェクトの目的は完璧なコードではなく、期限内に動くサイトを出すこと」 |

### Step 3: 発生確率と影響度で分類する

各失敗モードに以下を割り当てる：
- **発生確率**: 高 / 中 / 低
- **プロジェクト目的への影響**: 高（目標達成を阻む）/ 中（目標達成の質を下げる）/ 低（見た目だけの問題で目標に影響しない）

タスク完了そのものではなく、プロジェクト目的への影響度を優先して並べ替える。

### Step 4: 予防策を定義する

発生確率・影響度のいずれかが「高」の失敗モードそれぞれについて、実装の前または実装中に取るべき具体的な予防策を1つ定める。

### Step 5: チェックポイントとして組み込む

予防策を、タスク内の検証チェックポイントに変換する。全チェックポイントを最後にまとめて行うのではなく、それぞれ適切なタイミングで実行する。

## 適用の目安

| タスクの種類 | プレモーテムの深さ |
|-----------|-----------------|
| 新機能・新画面の実装 | フル（Step 0〜5、文書化して報告） |
| バグ修正 | 絞り込み（Step 1〜4、失敗モード2〜3個） |
| リファクタリング | フル（Step 0〜5、プロジェクト目的との整合性を重視） |
| スタイル・CSS変更 | 絞り込み（Step 1〜4、デザインの忠実性を重視） |
| 設定・インフラ変更 | フル（Step 0〜5、環境とロールバックを重視） |
| 単一ファイルの軽微な修正 | 頭の中でのみ（Step 1の整合性チェックのみ、文書化不要） |

## よくあるプロジェクトレベルの失敗パターン

1. **タスクは完了してもプロジェクトは進んでいない**: 個々のタスクは全部「完了」したのに、プロジェクトはリリースされなかった。個々のタスクがクリティカルパスと噛み合っていなかった。
2. **検証なしの「完了」**: 完了を宣言したが、テストも実行せず、デザインも確認せず、仕様との照合もしていない。
3. **仕様のドリフト**: ユーザーの意図ではなくAIの想定で作ってしまった。実装と仕様のズレが、多数のタスクを経るうちに気づかれないまま広がった。
4. **連鎖的な破壊**: 1つのコンポーネントを変更したら5つ壊れた。プロジェクトの動作中の状態に対する影響範囲を確認していなかった。
5. **早すぎる最適化**: プロジェクトがまず基本機能を必要としている段階で、コード品質・パフォーマンス・アーキテクチャに時間を使ってしまった。
6. **スコープクリープ**: 「ついでに」で無関係な変更を持ち込み、新たなバグを生みクリティカルパスを遅らせた。

## 禁止パターン

「このタスクは単純だから」という理由でプレモーテムを省略することを禁止する。
理由：単純だと思われているタスクほど、回避可能な失敗が最も起きやすい。単純さは過信を生む。

タスクをプロジェクトの目的への影響を考えずに単体で評価することを禁止する。
理由：「動く」だけでプロジェクトの目標に貢献しないタスクは、労力の無駄である。

予防策なしに失敗モードだけ列挙することを禁止する。
理由：対策のないリスクの洗い出しは、分析ではなく単なる不安の表明にすぎない。

複数手順を伴うタスクで、プレモーテムを頭の中だけで済ませることを禁止する。
理由：書き出さない分析は消えてしまう。3ファイル以上または複数手順の実装では、簡潔なプレモーテムの要約を必ず含めること。

**確信度**: High

## プレモーテム報告フォーマット（複数手順タスク向け）

実装に着手する前に、次のセクションを含めること：

```
## Pre-Mortem Analysis
**Project purpose**: {プロジェクトの目的文書から取った一行要約}
**Task alignment**: {このタスクがプロジェクトの目的にどう資するか}

| Failure Mode | Likelihood | Project Impact | Preventive Action |
|-------------|-----------|----------------|-------------------|
| ... | High/Med/Low | High/Med/Low | ... |
```

単一ファイルの軽微な変更では、Step 1の頭の中での整合性チェックのみで十分であり、文書化した報告は不要である。

## 他の思考プロトコルとの関係

- **Essential Thinking**は「これは本質的な問題か？」と問う（何を解くかを選ぶ前に）
- **Pre-Mortem**は「プロジェクトが失敗したとき、このタスクは原因の一つだったか？」と問う（どう解くかを選ぶ前に）
- **Intentional Execution**は「ユーザーの真の意図は何か？」と問う（何を作るかを選ぶ前に）

この3つのプロトコルが、実装前の思考の連鎖を構成する：意図 → 本質 → プレモーテム → 実行。
