# material-writing（教材の書き方）

教材の本文（Step）を書く・書き直す・読み返すときの完全な手順。
このファイルの文は、どの教材にも同じ。教材ごとに違う値（1 つのコードブロックの行数・コードの 1 行目に書く書き込み先の形・
学習者像）は、依頼文から読む。依頼文に書かれた値が、このファイルの一般の書き方より先に効く。

出典: 6 つの手順・密度の考え方・5 つの不在は、CC BY 4.0 の文章術の束を日本語の教材向けに抜き出して書き直した物。
なぜを教える節は、MIT の束の 3 原則を使っている。作者・URL・ライセンスは `reference/attribution.md` に書いてある。

## 恒久ルール: 教材は実コードを編集しながら、その場で書く

1 Step は「作業ツリーの実コードを1か所変える → 動かして確かめる → その差分と理由を Step に書く」で1単位とする。
教材に載せるコードは作業ツリーの実ファイルから写し、手で打ち直さない。
後からまとめて書くことも、先に教材を書いてからコードを合わせることも禁止する。

このルールがある理由: 手で打ち直したコードは、どこかで1字ずれる。ずれたコードを写経した読者は、
教材のとおりに打ったのに動かない状態で止まる。読者には教材とコードのどちらが間違っているか判断できない。

教材の正解は、作業ツリーの実コード（正解のコード）にある。教材とコードが食い違ったら、教材を直す前に
「コードの書き方が初心者に教えられるか」を確かめる。教えられないならコードを先に直し、テストを通してから教材に写す。

## 優先関係

ルール同士がぶつかったときは、上の行を採る。

| 順位 | ルール | 例 |
|---|---|---|
| 1 | 恒久ルール（実コードから写す） | 説明が書きにくくても、コードを教材の都合で書き換えない |
| 2 | 教材固有の要請（手順を省かない・なぜを書く） | ブログなら削る冗長さも、手順なら残す |
| 3 | 定型句は0回（B-7 の上限0の句） | 「を可能にします」は1回でも直す |
| 4 | 構文の技法（対比・三連・「つまり」）は密度の上限内で使う | 取り違えやすい2つを区別する対比は残す |
| 5 | 文体の好み（語尾の揺らし方など） | 書き手の判断 |

外部の文章術の原則は、後述の一致点だけを借りる。ぶつかったら、この skill を採る。

## 書く前に必ず通す思考プロセス（guide 04 の6手順）

<!-- Source: hana652/tech-writing-pack guide 04 — Collocation. CC BY 4.0. -->

この6手順は「書き始める前」と「書き直す前」の両方で実行する。
linter は語彙の選択ミスを検出できない。判定できるのは書き手だけ。

### 手順 1 — 偏愛語を疑う

以下の語が文に登場したら、いったん手を止める。

| カテゴリ | 典型的な偏愛語 |
|---|---|
| 動詞系 | 落ちる・壊れる・刺さる・効く・回る・動く・走る |
| 名詞系 | 設計・仕組み・構造・本質・流れ・全体像 |
| 形容詞・副詞系 | 解像度が高い・手触り・深い・シンプルな・綺麗な |

「設計」「構造」はコーディング教材で正当に使える語だが、抽象的な概念（情報・理解）に被せると擦り倒しになる。

### 手順 2 — 対象に実体があるか判定する

| 実体あり（OK） | 実体なし（擦り倒しの疑い） |
|---|---|
| 「DBスキーマ設計」→ 実際のテーブル定義がある | 「情報設計」→ 何の情報？どのテーブル？ |
| 「サーバーが落ちる」→ プロセス終了が実体 | 「体験が壊れる」→ 何がどう変わる？ |
| 「画面が再描画される」→ 描画の処理が実体 | 「本質がわかる」→ どの動作が変わる？ |

判定ルール: 名詞の指示対象を1文で説明できるか。できなければ擦り倒し。

### 手順 3 — NGなら比喩に逃げず具体へ書き直す

```text
❌ 「この情報が落ちると設計が壊れる」
✅ 「ユーザー ID が空のままだと、DB へ渡す検索条件が組み立てられずエラーになる」
```

比喩でごまかさない（「まるで積み木が崩れるように…」）。具体の動作に翻訳する。

### 手順 4 — 構文の癖を直す

| 癖のある構文 | 直す方向 |
|---|---|
| 「〜は、〜だった」（過去形で語る） | 現在形 or 命令形へ（「〜になる」「〜してください」） |
| 「AではなくB」の対比が1文内に同居 | 2文に分ける。否定する A を読者が本当に思い込みそうか先に確かめる |
| 「〜という」の入れ子 | 「〜とは」で定義文に |
| 「〜のようなもの」 | 実体で定義する |
| 並列以外の読点（「〜は、」「〜が、」「〜ので、」「〜すると、」の息継ぎ） | 読点は入れ替えても意味が変わらない並列の要素の間（「A、B、C」「Aも、Bも」）にだけ打つ。読点が無いと読みにくい文は2文に分けるか語順を変える。読点を足して済ませない |
| 和文と英字・行内コードがくっつく（「のでStep 0」「とき`x`」「Day 15の」） | 間に半角空白を1つ入れる。`Day 15` や `Step 3` の番号の後ろも空ける。ほかの数字と「、」「。」の前後は詰める。読点で区切らない。画面・初期データ・図の文字を引くときは元の表記のまま書く |

### 手順 5 — 動詞・助詞・形容詞の選択ミスを正す

慣用句の破壊に注意（「課題を改善する」→「課題を解決する」「改善策を実施する」）。

| NG | OK |
|---|---|
| 「問題を改善する」 | 「問題を解決する」 |
| 「知識を身につける」（教材で頻出） | 「〜できるようになる」（行動目標に変換） |
| 「うまく動く」 | 「エラーなく起動し、〇〇を返す」 |
| 「ちゃんと設定する」 | 「.env に DATABASE_URL を記述する」 |

### 手順 6 — 重言・翻訳調を消す

| 重言 | 翻訳調（英語直訳臭） |
|---|---|
| 「まず最初に」→「まず」 | 「〜することができます」→「〜できます」 |
| 「約〜程度」→「約〜」 | 「〜という点に注意」→「〜に注意」 |
| 「返り値を返す」→「返す」 | 「行うことが必要です」→「必要です」 |

## レジスタ注意（教材と外部発信の違い）

- 教材の地の文は敬体（です・ます）で、軽い親しみを持たせる。AI 臭・翻訳調・偏愛語は排除する。

## 文体スペック

### 基調 — ですます体（くだけた口調・方言の混入に注意）

地の文（コードブロック・引用以外）はすべて **ですます体**。
**AI の応答スタイルがくだけた口調や方言でも、教材本文には持ち込まない。** ここが最も混入しやすい。

| 許可される語尾 | 禁止される語尾 |
|---|---|
| です / ます / ました / でした | だ / だぞ / だろ / しろ |
| しましょう / してみましょう | 方言やくだけた口調の語尾 |
| ですね / ますね | 命令形単体（「書け」「使え」「確認しろ」） |
| ポイントです / 確認してみましょう | 話し手の人物を感じさせる一人称 |

### 禁止カテゴリ — AI典型構文

| ❌ NG | ✅ OK |
|---|---|
| することができます | できます |
| これにより | だから / なので / よって |
| 〜と言えるでしょう | 〜です / 〜になります |
| 〜ではないでしょうか | 〜ですよね |
| いかがでしたでしょうか | （削除する） |
| ここでは〜について解説します | （削除して本文から始める） |
| さまざまな場面で | （削除するか具体例を書く） |
| 言うまでもありません / あらゆる観点から | （削除するか具体項目を列挙） |

### 禁止カテゴリ — 英語直訳調（翻訳文感はここ）

| ❌ NG | ✅ OK |
|---|---|
| 〜することは可能です | 〜できます |
| 〜について言及 | 〜について / 〜を紹介 |
| 〜を実施します | 〜します / 〜を行います |
| 〜に関しても同様です | 〜も同じです |
| 〜を可能にします | 〜できるようになります |

## 密度の考え方（guide 07・08）

<!-- Source: hana652/tech-writing-pack guides 07, 08. CC BY 4.0. -->

AI 文体の違和感は、誤用ではなく頻度で生じる（guide 07 法則1）。「AではなくB」も「〜するだけ」も単体では正しい日本語で、
人間も使う。AI はそれを人間の数倍の密度で使う。だから対策は禁止ではなく上限で、判定は「表現の有無」ではなく「密度の超過」で行う。

もう1つ覚えておく法則がある。ルールを守らせると、守り方そのものが型になる（法則5）。
上限ぴったりまで均等に使う、全節のリードを同じ述語で始める、といった新しい機械っぽさが出る。
だから「2回目以降は形を変える」を、上限と対で守る。

### guide 08 から採った項目

B-1・B-2・B-7・A-3・B-9・B-11・B-10・B-6・B-12・B-14 は、教材に効く項目を束の guide 08 から選んだ物で、採る理由は guide 08 の記述による。
B-8 は機械判定が無く、通し読みで人が見る。

| 項目 | 採否 | 教材での使い方 |
|---|---|---|
| B-1 対比構文 | 採る（密度で） | 取り違えやすい2つ（例: 2つの設定ファイル、2つの関数）を区別する対比は正当。誰も主張していない誤解を否定してから入る型と、改行して太字の結論を置く演出は直す |
| B-2 三連反復 | 採る（段落内・密度で） | ですます体は文末が揃いやすい。番号付き手順の文末が揃うのは正当。まとめで「〜しました」を3回重ねる定型は直す |
| B-7 定型句・指紋 | 採る（0回） | 「してくれます」（ツールの擬人化）、「を可能にします」は直す |
| A-3 同一強調語 | 採る（1回） | 「一番上」「一番外側」のような位置の意味は正当。「一番大事」「一番のヤマ場」は直す |
| B-9 「つまり」 | 採る（密度で） | 用語の言い直しは正当。言い直すだけの要約と見出しの「つまり」は直す |
| B-11 「するだけ」 | 採る（密度で） | 手順の終わりが本当に1操作なら正当。「学んだこと」欄の誇張は直す |
| B-6 メタ談話予告 | 採る（上流の上限のまま） | 「ここからが今日のいちばん面白いところです」型は削っても情報が減らない |
| B-8 円環・同型締め | 採る（人が見る・機械判定なし） | 各 Day の締めを同じ型にしない。機械では拾えないので通し読みで見る |
| B-10 文体混在 | 採らない（機械判定に任せる） | ですます体の一貫は `edu-creator check` の `tone` が別に見る |
| B-12 換算・B-14 伝聞 | 採る（上流の上限のまま） | 教材で数字を言い換え続けない。出典の無い「知人が」は書かない |

## 5つの不在（思考の問題として理解する）

<!-- Source: hana652/tech-writing-pack guide 03 — Anti-AI 5 Absences. CC BY 4.0.
     以下は原文（ブログ記事向け）に忠実な要約。教材固有の要請は「教材レジスタでの読み替え」に分けて書く。 -->

5つの不在は「禁止表現のリスト」ではなく、思考の欠落を指す。表現を潰して回るのではなく、なぜその思考が生まれるかを理解する。

1. **態度の不在** — AI は全トピックを同じ温度で書く。人間は大事な所に力を入れ、どうでもいい所は流す。書く前に「このテーマのどこが重要か」を1行で言語化し、それを文章の温度にする。
2. **勇気の不在** — AI は「〜と言えるでしょう」で保険をかける。各セクションで「結局どうなのか」を最低1つ言い切る。断言できないときは条件を切って、それぞれ言い切る。
3. **省略の不在** — AI は聞かれていないことまで網羅しようとする。「ここを読み飛ばされても主旨は伝わるか」を試し、伝わるなら削る。
4. **リズムの不在** — AI の文章は文の長さが均一になる。長い文の後に短い文、長い段落の後に1文だけの段落、という緩急をつける。
5. **沈黙の不在** — AI はすべての段落に結論とまとめを書く。あえて結論を書かず、問いだけで段落を閉じることもある。

詳細と症状パターン①〜⑮は、元の束のガイド 03 を読む（場所は `reference/attribution.md`）。

### 教材レジスタでの読み替え（hana652 の原則とは別の、教材固有の要請）

- **手順は省略しない**（3 とは逆方向）。「同様に」「残りも」「以下略」で手順を端折ると、初心者はコードを追えなくなる。
- **「なぜ」は明示的に書く**（5 とは逆方向）。初心者教材では「こう書きます」の後に必ず理由を添える。次節で扱う。

## なぜを教える — メンタルモデルを渡す（手順書化の禁止）

<!-- Source: Xamfonos/technical-writing-best-practices (MIT)。開発者向けのトーンは採らず、3原則の考え方だけを使う。 -->

「これを書け → 確認」の羅列は手順書であって教材ではない。コードブロックの後には必ず「なぜこう動くか」を書く。

1. **手続きの前に、その手続きが解く問題を示す。**（Introduced Abstractions）「一覧を返す関数を書きます」ではなく「一覧画面は全件を取ってくる必要があります。その入口を1つ作ります」から入る。
2. **新しい概念は、読者が既に知っている論理構造に結びつける。**（Mental Model Anchoring）引数・戻り値が何を保証しているかを、暗記ではなく理屈で分かる形にする。
3. **段階的な洞察 — 一度に全部渡さない。**（Layered Insight）概念→仕組み→実装の順に層を分け、前の日の理解の上に積む。

判定基準: 読者がこの節を読んだあと、次の似た手続き（一覧の次の新規作成など）を自力で書ける見込みがあるか。
無ければ「なぜ」が足りない。手順を増やすのではなく理由を足す。

## 執筆前チェックリスト

- [ ] 6手順を実行した（偏愛語スキャン → 実体判定 → 具体化）
- [ ] 対象 Day の完成定義を1文で書いた（「Day X 終了時点で読者は〇〇ができる」）
- [ ] 前の Day で習得済みの前提知識をリストアップした
- [ ] 新出の専門用語を洗い出し、初出箇所に注釈（括弧書き）を入れた
- [ ] 載せるコードを、作業ツリーの実ファイルから写す準備ができている（恒久ルール）

## 書いた後の検査

検査は、この実行の中では打たない。edu-creator が実行の後に回す（どれが・いつ回るかは `curriculum-quality-gate`）。
この実行では、書いた Step を、次の順で自分で読み返す。

1. 恒久ルール: 教材のコードが、作業ツリーの実ファイルと一字も違わない
2. 6 つの手順: 偏愛語・実体のない名詞・翻訳調が残っていない
3. 「なぜ」: 各コードブロックの直後に、なぜこう動くかがある

検査に落ちたら、通るまで書き直す。検査の側は変えない。

### コードブロックの長さの例外

コードブロックは、依頼文の行数以下が原則。読者が 1 ファイルとしてそのままコピーする必要があり、分割すると途中状態や
手作業の結合を生む場合だけ、対象フェンスの直前に次の印を置ける。

```markdown
<!-- code-block-length-exception: complete-copy-unit -->
```

例外ブロックには filepath 行が要る。上限以下のブロックへの例外、印だけを置くこと、印とフェンスの間に本文を挟むことは失敗になる。

### 冷えた読み手

別のエージェントが完全な初心者として全範囲を読む採点は、Day を書き終えた後に edu-creator が回す（`edu-creator judge run`）。
読み手像は、依頼文の「学習者」の行から決まる。この実行では回さない。人間の初心者テストを行っていない場合は、実施済みと書かない。
